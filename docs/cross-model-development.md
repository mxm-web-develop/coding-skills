# 用不同模型规划和开发

目标是让擅长规划的模型先把任务确定清楚，让后续执行模型可以沿用决定完成开发。用户只需要说“把这个功能的计划确定好，之后我换模型执行”或“按之前的计划继续”。换编辑器不会创建第二份计划；不用清空聊天来使用或验证这个流程。

## 四项补齐

| 原来的缺口 | v1.1.0 的处理 | 如何检查 |
| --- | --- | --- |
| 计划过于笼统，执行者仍要重新设计 | 任务交接包含接口、约束、入口、步骤、边界、测试和回交条件 | 缺关键内容时不能建立交接；既定测试不能换成较弱命令 |
| 给用户的摘要不足以支撑执行 | 用户看短摘要，执行模型读取当前任务的完整相关资料和最新进度 | 超出预算明确报错，不能裁掉约束；未完成的依赖不能跳过 |
| 失败后擅自改方案或反复重试 | 记录规划者、执行者、评审者；冲突带证据交回；规划者记录解决决定 | 未解决前继续执行失败；执行者自审及自行扩大重试预算失败 |
| 旧文档、误判技术栈污染记忆 | 扫描候选与确认事实分开；记录来源、核实人和版本；旧事实可追溯 | 修改来源后旧交接失效；更新事实必须明确取代旧版本 |

## 一次完整使用

1. 用规划模型讨论需求与设计。必要的产品选择由你决定；已决定的内容不用反复确认。规划模型把近期任务拆成可独立验证的小项，并准备交接资料。
2. 切换执行模型或 IDE，说“继续当前任务”。Agent 从项目里读当前计划、已确认约束、代码入口和上次进度。
3. 对尚未验证过的模型，先完成一个有代表性的小改动。看它能否遵守范围、通过行为测试，以及识别需要回交的问题。
4. 简单实现问题由执行模型处理。涉及未确定的接口、权限、架构或超出失败次数时，模型保存证据并停止改动。你可以切回规划模型处理，随后继续原任务。
5. 评审模型检查代码和真实测试结果。你按给出的操作步骤验证，通过后完成任务并归档过程记录；不通过就在原任务上修复。

模型和角色名称由你所用的 IDE/Agent 声明。工具能检查记录及命令，不能认证背后的模型，也不能阻止任意程序绕开工具直接编辑文件。它不包含第三方模型调用器，不会偷偷购买调用或切换供应商。

## 如何评估执行模型

使用同一任务类型、相同已确定的要求和相近代码基线，比较以下真实结果。不要把“聊天上下文清空成功”当成能力结论。

- 常规开发：实现边界明确的小功能，测试可观察的行为而非仅检查进程退出码。
- 边界处理：例如 CSV 内含逗号、引号、换行、空选择以及越权数据。
- 遇到矛盾：故意保留一个必须由规划者解决的接口问题，看执行者是否提交证据并停止猜测。
- 连续失败：查看它能否在预算内定位问题，失败后是否升级处理。
- 事实变化：修改需求或配置，看它是否拒绝使用过期计划。

每次保存模型标识、工具条件、任务与交接版本、测试结果、评审结论、偏离计划情况、返工次数、升级处理次数。只有实际完成这些任务才给出“适合这一类任务”或“需要监督”的结论；未测的模型保持“未测试”。记录模板见 [model-evaluation.json](examples/model-evaluation.json)。不要用脚本模拟结果填充真实模型成绩。

成本包括规划、执行失败重试、返工和复核。无供应商用量或账单证据时留空；不能把未知费用当零，也不能从某模型单价较低推导总成本更低。当前版本提供执行协议和回归测试，**没有 MiniMax/K2 的真实对比数据**。

## 从旧项目升级

升级先保存旧记录与进度，再核对现行要求。v1.0 的任务无需重建；切换执行模型前，为剩余工作补齐交接资料并核实工程画像。已完成历史保持原样，未验收任务仍等待验证。参见[升级说明](upgrade.md)。

技术命令与示例参见 [CLI 参考](cli-reference.md)；实际使用时由 Agent 操作。
