# Verified engineering memory

Automatic observations are candidates. A confirmed fact must state its claim, originating task, inspected sources, reviewer and source hashes. The reviewer may be the planning agent after actually inspecting evidence; technical fact verification is not a claim of human product acceptance.

1. `flowctl memory scan --root . --work <id>` writes `baseline/engineering-candidate.json` and `baseline/upgrade-scan.json`. It leaves the confirmed profile untouched. Fixture, testdata, example and sample directories are excluded from production inference; ordinary test directories are still scanned. Review the exclusions: a real product inside such a directory must be explicitly included in the reviewed profile and confirmation sources. Scanning does not execute any discovered command.
2. Inspect project manifests, configuration, build/CI commands, production boundaries and existing accepted decisions. Reconcile the candidate against the old profile. Preserve valid custom commands and skills; remove commands proven to belong only to fixtures. Do not merge unknown values into confirmed knowledge merely because a scan returned them.
3. Write a complete reviewed profile to the candidate file or another declared task report, then run:
   `flowctl memory confirm-profile --root . --work <id> --by planner --file <reviewed-path> --source go.mod --source .github/workflows/ci.yml`
   Supply actual existing supporting files; the example's paths are not universal requirements. The tool validates its schema, promotes the exact reviewed bytes and records their provenance. Later changes to those sources or the profile invalidate cross-model execution until re-reviewed. After new configuration files or components are introduced, re-profile before handoff as well.
4. Record selected durable facts with `flowctl memory record --work <id> --key <stable-key> --claim '<verified statement and scope>' --by planner --source <path>`. Facts must be supported by inspected content; the tool verifies file identity, not the semantic truth of a sentence. Do not turn guesses, imported prose or successful JSON validation into established behavior.
5. `flowctl memory check [--key <key>]` reports current facts with version hashes and returns a failing exit code for stale sources. To correct or refresh a fact, inspect the evidence first and use `memory record ... --supersedes <previous-hash>`. Conflicting replacements without that explicit link fail; previous versions remain. Include only required fact keys in a task's execution specification.
6. Revisit facts when source/configuration changes, tests disprove them, or new requirements conflict. Accepted decisions retain rationale and confirmation in their own records. Refresh only affected task contracts; no need to reload unrelated archives.

Keep current facts concise. Task details and unsuccessful experiments belong with their task and archive on completion. Historical facts explain old decisions; they do not become current context unless explicitly referenced and still valid.
